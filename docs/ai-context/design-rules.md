# CareerPath — Design Rules

Этот файл задаёт **общие системные принципы UI** для CareerPath.

Важно:
- этот файл **не является источником конкретной экранной композиции**
- этот файл **не разрешает придумывать новый визуальный стиль**
- конкретные визуальные решения, layout экранов, структура секций, ритм отступов, стили компонентов и screen-specific правила задаются в:
  - `ui-adaptation-rules.md`
  - утверждённых design screens / Figma screens

Если есть конфликт:
1. `ui-adaptation-rules.md`
2. approved design screens
3. `design-rules.md`

Этот файл описывает **только универсальные правила дизайн-системы**.

---

## 1. Общий дизайн-подход

CareerPath — это цифровой сервис профориентации для школьников и абитуриентов.

Интерфейс должен:
- вызывать доверие
- быть понятным подростку
- быть удобным и для родителя
- быть современным, чистым и спокойным
- быть пригодным для длительного чтения
- быть mobile-friendly
- быть масштабируемым как продуктовая система

Интерфейс не должен:
- выглядеть детским
- выглядеть визуально шумным
- выглядеть как generic startup template
- выглядеть как enterprise-heavy admin panel
- выглядеть как игровой квиз
- выглядеть как набор несвязанных экранов

---

## 2. Дизайн-принципы

Основные принципы:
- clarity first
- trust first
- calm visual language
- readability first
- accessibility-aware design
- component reuse over ad-hoc layouting
- consistency across screens
- simple before decorative
- practical before expressive

Каждый новый экран или изменение экрана должны:
- использовать существующие компоненты и паттерны
- не ломать визуальную систему
- не создавать новый стиль без причины
- поддерживать уже существующую иерархию интерфейса
- оставаться совместимыми с дизайн-системой продукта

---

## 3. Роль этого файла

Этот файл нужен, чтобы зафиксировать:
- общие принципы визуальной системы
- требования к consistency
- требования к typography / spacing / colors / surfaces
- правила component reuse
- общие expectations для accessibility и responsive behavior

Этот файл **не должен использоваться** как основание для:
- свободного редизайна экранов
- перестройки layout по собственной инициативе
- изменения page composition без явного основания
- интерпретации Figma “по мотивам”

---

## 4. Визуальный стиль

Общий стиль интерфейса должен быть:
- современным
- минималистичным
- аккуратным
- спокойным
- доверительным
- образовательным / карьерным
- мягким, но не “детским”
- чистым, но не пустым

Настроение интерфейса:
- спокойный
- понятный
- поддерживающий
- сфокусированный
- серьезный, но не тяжёлый
- дружелюбный, но не развлекательный

---

## 5. Цветовая система

Используй design tokens.

Базовые принципы палитры:
- светлый нейтральный фон
- высокий контраст основного текста
- один основной акцентный цвет
- один дополнительный позитивный цвет
- мягкие системные состояния
- ограниченное использование акцентного градиента
- мягкие и спокойные границы поверхностей

Правила:
- цвета должны быть пригодны для длительного чтения
- интерфейс не должен перегружаться насыщенными цветами
- цвет должен усиливать иерархию, а не создавать шум
- цветовые значения должны быть токенизированы
- нельзя использовать случайные page-specific colors без включения в систему токенов

Нельзя:
- кислотные цвета
- резкие контрастные комбинации без необходимости
- чрезмерное количество акцентных цветов
- использовать цвет как единственный носитель смысла

---

## 6. Типографика

Типографика должна быть:
- крупной и ясной
- хорошо читаемой на мобильных устройствах
- с выраженной иерархией
- удобной для длинных блоков текста
- последовательной по всей системе

Правила:
- использовать понятный sans-serif stack
- должна быть заметная разница между h1 / h2 / h3 / body / small
- вторичный текст не должен быть слишком мелким
- заголовки должны быть визуально сильными, но не декоративными
- длина строк должна оставаться комфортной для чтения
- typography scale должна быть оформлена через design tokens или системные правила

Нельзя:
- декоративные шрифтовые решения без явной причины
- мелкий и блеклый body text
- хаотичную типографическую шкалу
- использовать разные визуальные правила для одинаковых уровней заголовков

---

## 7. Пространство и layout

Придерживайся единой системы spacing.

Нужно:
- ритмичные вертикальные отступы
- визуально стабильные внутренние paddings
- ограничение ширины контента на больших экранах
- хороший responsive behavior
- layout без визуального развала
- единая система контейнеров и секций

На desktop:
- контент не должен бесконтрольно растягиваться на всю ширину
- блоки должны легко читаться
- не должно быть ни пустынности, ни перегруженности

На mobile:
- крупные tappable areas
- формы и контент в один столбец там, где это логично
- понятная вертикальная структура
- комфортные интервалы между интерактивными элементами

Нельзя:
- случайные отступы
- слишком плотные layouts
- слишком разреженные layouts без смысловой причины
- full-width текстовые блоки с плохой читаемостью
- page-specific spacing logic без системного обоснования

---

## 8. Поверхности, карточки и границы

Интерфейс должен опираться на систему поверхностей.

Базовые правила:
- primary surfaces должны быть чистыми и читаемыми
- границы должны быть мягкими и аккуратными
- карточки должны выглядеть как часть одной системы
- тени должны использоваться очень сдержанно
- радиусы должны быть последовательными

Нужно:
- повторяемые паттерны card surfaces
- единые правила border / radius / padding
- token-based подход для surfaces
- различать primary surface, muted surface, highlighted surface

Нельзя:
- heavy shadows как основной визуальный инструмент
- разные типы карточек без системного паттерна
- случайные сочетания border, radius и shadow
- визуальную перегруженность поверхностей

---

## 9. Компонентный подход

CareerPath должен собираться как design-in-code system.

Все UI-решения должны стремиться к:
- reusable primitives
- reusable product components
- consistent variants
- shared tokens
- predictable interaction patterns

Каждый новый экран должен:
- переиспользовать существующие компоненты
- не добавлять одноразовые UI-паттерны без необходимости
- не плодить уникальные версии одинаковых сущностей
- опираться на component inventory проекта

Нужно:
- строить UI через shared components
- использовать variants вместо ручного дублирования
- выносить повторяемые паттерны в отдельные компоненты
- поддерживать визуальную и поведенческую консистентность

Нельзя:
- создавать одноразовую верстку там, где уже есть повторяемый паттерн
- смешивать разные визуальные языки внутри одного продукта
- делать page-specific стиль вместо компонентной системы

---

## 10. Состояния интерфейса

Во всех ключевых местах должны быть предусмотрены:
- hover states
- focus states
- selected states
- disabled states
- loading states
- empty states
- error states
- success states

Эти состояния должны быть:
- заметными
- спокойными
- consistent across the product
- доступными с точки зрения восприятия
- не слишком агрессивными визуально

Нельзя:
- делать состояния “для галочки”
- делать inaccessible focus states
- использовать слишком яркие/стрессовые состояния без причины
- скрывать системные статусы от пользователя

---

## 11. Объяснимость и читаемость результата

Поскольку продукт строится вокруг рекомендаций и профориентации, интерфейс должен поддерживать explainability.

Нужно:
- делать результаты визуально понятными
- помогать пользователю быстро понять, что ему показывается и почему
- структурировать объяснения короткими и читаемыми блоками
- использовать простой и понятный язык
- поддерживать сканируемость контента

Нельзя:
- превращать рекомендации в “магический черный ящик”
- прятать объяснения в длинные перегруженные тексты
- перегружать экран аналитикой без необходимости
- использовать визуальную драматизацию вместо ясности

---

## 12. Accessibility

Интерфейс должен быть accessibility-aware.

Нужно:
- достаточная контрастность
- понятные focus states
- читаемые размеры текста
- предсказуемое поведение интерактивных элементов
- semantic-friendly markup
- визуальная иерархия, помогающая навигации

Нельзя:
- опираться только на цвет для передачи смысла
- делать слишком маленькие кликабельные области
- использовать плохо различимые текстовые стили
- игнорировать keyboard/focus behavior в критичных местах

---

## 13. Responsive behavior

CareerPath — web-first продукт с обязательным качественным responsive UI.

Правила:
- экран должен оставаться читаемым и функциональным на mobile / tablet / desktop
- при уменьшении ширины layout должен упрощаться, а не ломаться
- важные действия должны оставаться доступными
- компоненты не должны терять смысл при адаптации
- grid patterns должны иметь предсказуемое поведение

Нельзя:
- делать desktop-first layout без mobile adaptation
- допускать переполнение текста или визуальный развал карточек
- создавать слишком сложные адаптивные схемы без необходимости

---

## 14. UX-тональность

Тон интерфейса должен быть:
- спокойным
- уважительным
- понятным
- поддерживающим
- доверительным
- не давящим

Нужно:
- ясные CTA
- понятные тексты
- low-stress interaction design
- дружелюбная подача без инфантилизации

Нельзя:
- агрессивный marketing tone
- игровой тон там, где нужен серьезный выбор
- перегруженные микрокопирайты
- визуальные решения, повышающие тревожность

---

## 15. Что нельзя делать на основании этого файла

Этот файл не разрешает:
- проектировать новый стиль “с нуля”
- менять структуру утвержденных экранов на свой вкус
- перестраивать layout, если screen-specific rules уже заданы в `ui-adaptation-rules.md`
- заменять approved design screens собственной интерпретацией
- вводить новый UI language без прямой необходимости

Если для экрана уже есть:
- approved screenshot
- approved Figma screen
- screen-specific adaptation rule

то именно они определяют:
- композицию
- порядок секций
- стиль компонентов
- ритм отступов
- тип layout

---

## 16. Правило приоритета

При любых визуальных решениях следуй такому порядку:

1. `ui-adaptation-rules.md`
2. approved design screens / Figma screens
3. `design-rules.md`

Если есть неоднозначность:
- не импровизируй
- не редизайнь
- не придумывай новый паттерн без необходимости
- придерживайся существующей визуальной системы

---

## 17. Ожидаемый результат

Финальный интерфейс должен быть:
- целостным
- спокойным
- современным
- объяснимым
- доверительным
- читабельным
- построенным на reusable components
- устойчивым к масштабированию

Он не должен ощущаться как:
- шаблонный SaaS UI
- случайный набор экранов
- переукрашенный лендинг
- перегруженный дашборд
- игровой продукт
